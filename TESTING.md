# Звіт про тестування та вимірювання покриття (TESTING.md)

## 1. Як запускати тести
Усі тести запускаються через `pytest` з кореневої директорії проєкту з активованим віртуальним середовищем:

```bash
# Базовий запуск (з автоматичним підрахунком покриття за налаштуваннями pyproject.toml)
pytest

# Стислий запуск без звіту покриття (якщо потрібно)
pytest -q -o addopts="-q"

# Запуск окремої підсистеми або тестів
pytest tests/domain
pytest tests/services
pytest tests/sources
pytest tests/test_cli.py

# Запуск із вимірюванням тривалості найповільніших тестів
pytest --durations=3
```

## 2. Що покрито тестами
Проєкт структуровано за пірамідою тестування, покрито всі архітектурні рівні:
- **Доменний рівень (`tests/domain/`):**
  - `test_text.py`: параметризовані тести функції `normalize_title` (різні регістри, зайві пробіли, табуляції).
  - `test_models.py`: інваріанти моделі `Book` (заборона порожньої назви, порожнього автора, нульових чи від'ємних сторінок), незмінність (`frozen=True`), обчислення ключа `key`, злиття дублікатів у множині `set`, властивість `is_large_book` з граничними значеннями (499 vs 500).
  - `test_parsing.py`: перевірка функцій парсингу сирих словників `to_book` та приведення числових значень `parse_pages`.
- **Сервісний рівень (`tests/services/`):**
  - `test_schemas.py`: валідація моделі межі `BookIn` (приведення числових рядків, перетворення текстових значень на `None`, видалення зайвих пробілів через виклик доменної функції `normalize_title`, перехоплення `ValidationError`).
  - `test_pipeline.py`: агрегація статистики, дедуплікація між джерелами, обробка порожнього джерела, лінивість конвеєра (`test_parse_all_is_lazy` з нескінченним генератором).
  - `test_logging.py`: тестування запису попереджень у `caplog`, перехоплення `SourceError`, збереження вихідної причини `__cause__`, маскування секретів `mask()`.
- **Шар адаптерів (`tests/sources/`):**
  - `test_jsonl.py`: читання JSON Lines, пропуск та логування битих рядків (`skip malformed line`), ігнорування порожніх рядків.
  - `test_json_array.py`: читання класичного JSON-масиву через `JsonSource`, обробка відсутності файлу.
  - `test_csv.py`: читання CSV-файлів із роздільником `;` через `CsvSource`, обробка відсутності файлу.
- **Наскрізні тести CLI (`tests/test_cli.py`):**
  - Запуск програми через `sys.argv`, перевірка підсумкового виводу в `capsys`.
  - Перевірка кодів виходу: неіснуючий файл (`code == 1`), непідтримуваний формат (`code == 1`).
  - Перевірка пріоритетів конфігурації: аргумент `--log-level` перекриває системну змінну `LOG_LEVEL` та файл `.env`.

## 4. Висновок про межі показника покриття
Експеримент із кроку 6 (навмисна зміна пріоритету аргументу й налаштувань у `cli.py`: заміна `setup(args.log_level or settings.log_level)` на `setup(settings.log_level or args.log_level)`) наочно продемонстрував ключову межу показника покриття:
- Навіть при 100% покритті коду всі тести лишалися зеленими, хоча реальний баг зламав роботу прапорця `--log-level`.
- Жоден рядок не лишився невиконаним, але логіка пріоритету не перевірялася жодним `assert`.
- Лише додавання спеціального тесту `test_flag_beats_environment` з підміною налаштувань виявило помилку (`AssertionError: assert ['ERROR'] == ['DEBUG']`).
- **Головний висновок:** покриття чесно відповідає на запитання, *які рядки коду точно не перевірено*, але нічого не гарантує щодо того, *наскільки якісно й повно перевірено рядки, що виконались*.
